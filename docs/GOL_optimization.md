# Оптимизация чтения GOL (без промежуточного PBF)

Зафиксировано для возврата к работе. Идеи по ускорению пути `GOL → GeoObject`,
который сейчас проходит через промежуточный PBF.

## Текущее состояние

Путь чтения GOL (`src/gol.rs`, `GolSource::parse`) сейчас выглядит так:

```
gol query <region.gol> '<GOQL>' -f pbf   →  temp-файл .osm.pbf
osmpbf ElementReader                      →  читает PBF
PbfParser                                 →  грузит все ноды (node_coords),
                                             сам считает центроиды way/relation,
                                             извлекает адреса/POI
```

Из-за багов GOQL в `gol` 2.3.2 выполняется **два** запроса (адреса + POI/места),
их PBF-выводы конкатенируются.

## Куда уходит время (замеры)

- **Калининград** (28 МБ PBF, 546 825 фич):
  - 2 запроса `gol query -f pbf`: **~0,7 с**.
  - парсинг PBF + наша обработка: **~5,9 с**.
  - Для сравнения, `*`-режим: экспорт ~1,6 с + парсинг ~16,6 с.
- **Central Fed District** (868 МБ PBF, 15 385 790 фич):
  - `gol query '*' -f pbf`: **55,9 с** (747 МБ).
  - прямой PBF: парсинг **731 с** (110 млн нод).

Вывод: **промежуточный PBF — не главный тормоз.** Основная стоимость — наша
обработка на стороне osmpbf: загрузка всех нод в `node_coords` (HashMap) и
расчёт центроидов way/relation. Сериализация в PBF — лишь малая часть.

## Варианты ускорения

### 1. Стриминг PBF без temp-файла (минимальная выгода)

Передавать stdout `gol query -f pbf` напрямую в `ElementReader::new(stdout)`.

- Экономит только дисковый I/O, не сериализацию и не нашу геометрию.
- Пайплайн делает 2 прохода (сбор place-типов + основной), поэтому всё равно
  нужен файл либо два запроса.
- Выгода небольшая.

### 2. Прямое извлечение через CSV/GeoJSONL с центроидом (наибольшая практическая выгода)

`gol query` умеет отдавать готовый **центроид** (`--keys lon,lat` — WGS-84
центроид фичи) и теги. Например:

```bash
gol query region.gol '<GOQL>' -f csv \
  --keys id,lon,lat,addr:housenumber,addr:street,addr:city,addr:town,addr:place,addr:country,addr:postcode,historic,tourism,name,name:ru,place,landuse
```

Собирать `GeoObject` напрямую из CSV, **минуя PBF, osmpbf, загрузку нод и
расчёт центроидов** — центроид считает сам gol.

- Убирает главную часть ~5,9 с (и 731 с на больших регионах).
- `extract_address` / `extract_named_object` уже принимают
  `HashMap<String,String>` + `lat/lon`, поэтому рефакторинг в основном сводится
  к замене цикла чтения osmpbf на цикл чтения CSV.
- Понадобится CSV-парсер (крэйт `csv` или ручной) и аккуратная обработка
  колонок с тегами (лучше перечислять нужные ключи явно, чем парсить blob `tags`).
- Нужно сохранить два запроса (адреса + POI/места) и сбор place-типов из второго.

**Цена/риск:** меняется источник координат — **центроид gol ≠ наш центроид way**
(у нас среднее арифметическое нод, у gol геометрический/площадной). Координаты
чуть сдвинутся; это влияет на пространственный индекс и на дедуп POI (< 100 м).
Для адресов разница несущественна.

### 3. FFI к `libgeodesk` (C++) — «настоящая» интеграция

Читать GOL в процессе напрямую через C++-библиотеку, без подпроцесса и без
сериализации.

- Максимальная скорость и минимум накладных расходов.
- Требует C++20, CMake и C-шва поверх C++ API (шаблоны/итераторы) — высокая
  трудоёмкость.
- Это «этап 5» из `docs/PLAN_gol.md` в исходной формулировке.

### 4. Нативный Rust-читатель GOL

Разобрать бинарный формат GOL самим (тайлы, R-tree, глобальная таблица строк,
varint).

- Полная автономность и скорость, без внешнего бинаря.
- Самый высокий риск/усилия; формат публично не оформлен как открытая спека.

## Рекомендация

1. **Быстрый выигрыш — вариант 2** (CSV + центроид от gol): убирает и PBF-круг,
   и самую дорогую часть (ноды + центроиды). Оценку «в разы» подтвердить замером.
2. **Долгосрочно — вариант 3/4** (без подпроцесса и сериализации).
