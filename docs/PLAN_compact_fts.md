# План: встроенный полнотекстовый индекс в компактном формате (`.bin`)

## 1. Проблема

Сейчас `.bin` (компактный формат) содержит только:

- `String Pool` — словарь строк;
- `Named Index` — сортирован по имени, для префиксного поиска по целому полю;
- `Address Index` — сортирован по `(city, street, housenumber)`;
- `Record Block` — сортирован по `(lat, lon)`, для пространственного поиска.

Полнотекстового индекса (стемминг + несколько токенов + префикс) в файле нет.
Поэтому мобильная библиотека вынуждена строить свой индекс на устройстве, что
для региона «Россия» занимает много времени.

Цель: встроить в `.bin` готовый инвертированный индекс, чтобы устройство
только `mmap`-ило файл и искало, без построения индекса.

## 2. Что должно совпадать с SQLite-путём

В SQLite (`src/indexer.rs`) полнотекстовый поиск устроен так:

- для `Address` индексируются `country`, `city`, `street` после
  **русского snowball-стемминга** в нижнем регистре; `housenumber` и
  `postcode` — как есть (без стемминга);
- для `NamedObject` индексируются `country`, `city`, `name` после стемминга;
  `category` — как есть;
- поиск — `AND` по токенам, каждый токен с суффиксом `*` (префиксный поиск);
- FTS5 `prefix='2 3 4'` позволяет искать по первым 2–4 символам.

Компактный FTS-индекс должен давать те же результаты поиска, что и FTS5,
но храниться в `.bin` и читаться напрямую из mmap.

## 3. Общий дизайн

Добавляем в `.bin` **два инвертированных индекса**:

- `FTS Address` — токены из полей адреса;
- `FTS Named` — токены из полей именованного объекта.

Каждый индекс состоит из двух частей:

1. **Словарь токенов** — отсортированный список уникальных стеммированных
   токенов. Для каждого токена хранится смещение и длина его постинг-листа.
2. **Постинг-листы** — для каждого токена отсортированный список `record_idx`
   (индексы в существующем `Record Block`), закодированный дельтами + varint.

Такая структура — классический инвертированный индекс, и она не требует
FTS5/SQLite на устройстве.

### 3.1. Какие поля индексируем

| Индекс | Поля (стемминг) | Поля (без стемминга) |
|--------|-----------------|----------------------|
| `FTS Address` | `country`, `city`, `street` | `housenumber`, `postcode` |
| `FTS Named`   | `country`, `city`, `name`    | `category` |

Для v1 приоритет — `city` + `street` (адреса) и `name` (POI), как в запросе
пользователя («по имени улицы или объекта»). `country`/`postcode`/`category`
можно включить сразу, т.к. стоимость невелика.

### 3.2. Токенизация и стемминг

Единая функция, общая для `Indexer` и `CompactWriter` (иначе результаты
разойдутся):

- split по пробелам;
- lowercase;
- для текстовых полей — `rust_stemmers::Algorithm::Russian`.

Требуется рефакторинг: вынести `Indexer::stem_text` в отдельный модуль,
например `src/stem.rs` (`stem_text`, `tokenize`), и использовать его в обоих
местах.

Транслитерация **не поддерживается** и в этот план не входит: поиск идёт только
по кириллическим токенам.

## 4. Изменения формата (версия 2)

### 4.1. Базовый подход

- Поднимаем `version` в заголовке с `1` на `2`.
- Вводим **Section Directory** — таблицу секций, чтобы формат можно было
  расширять дальше без сдвига всех смещений.

Предлагаемое размещение:

```
[Header, 88 B, version=2]
[Section Directory]
[String Pool]
[Named Index]
[Address Index]
[Record Block]
[FTS Address: token dictionary]
[FTS Address: postings]
[FTS Named: token dictionary]
[FTS Named: postings]
```

`Section Directory` начинается сразу после заголовка (по фиксированному
смещению `88`). Каждая запись — `(id:u16, offset:u32, length:u32)` = 10 байт,
перед ними `count:u32`.

Читатель:
- читает `magic` и `version`;
- при `version >= 2` читает `Section Directory` по смещению 88;
- находит нужные секции по `id`;
- mmap и читает напрямую, без построения структур в памяти.

Существующие 4 секции (`string_pool`, `named_index`, `addr_index`, `records`)
получают свои `id`; их смещения по-прежнему продублированы в заголовке, чтобы
старые инструменты (`inspect_bin.py`) ломались минимально.

### 4.2. Идентификаторы секций (черновик)

| id | Секция |
|----|--------|
| 1 | String Pool |
| 2 | Named Index |
| 3 | Address Index |
| 4 | Record Block |
| 5 | FTS Address token dictionary |
| 6 | FTS Address postings |
| 7 | FTS Named token dictionary |
| 8 | FTS Named postings |

### 4.3. Layout словаря токенов

```
count:                u32
entries, для каждого:
  token_len:          u16
  token:              UTF-8, token_len байт
  postings_offset:    u32   (смещение в секции postings)
  postings_count:     u32   (число record_idx)
```

Словарь сортирован по `token` (байтово, но фактически по кодовым точкам после
lowercase). Префиксный поиск — бинарный поиск `lower_bound(prefix)` + линейное
сканирование, пока токен начинается с префикса.

Токены хранятся inline, а не через `String Pool`, по двум причинам:

- независимость от `u16`-лимита пула строк;
- локальность: словарь токенов читается целиком или кусками, постинги — по
  смещению.

### 4.4. Layout постинг-листов

```
count:              u32
postings:           varint-последовательность (LEB128)
```

Для каждого токена `postings` — отсортированный по возрастанию список
`record_idx`, закодированный как:

```
delta_i = record_idx_i - record_idx_{i-1}   (record_idx_0 — как есть)
bytes   = LEB128(delta_i)
```

`postings_offset` из словаря указывает на первый байт списка токена,
`postings_count` — число записей.

Опционально (фаза 2) — блоковое сжатие дельт (Simple16/PForDelta) и хранение
`freq:u8` для ранжирования. Для v1 достаточно varint-дельт.

## 5. Алгоритм поиска (на устройстве)

1. Нормализовать запрос так же, как при сборке: lowercase → стемминг каждого
   слова → список токенов (для `housenumber`/`postcode` — без стемминга).
2. Для каждого токена найти диапазон в словаре, где токен начинается с него
   (префиксный поиск), собрать его постинг-лист(ы).
3. Пересечь списки (AND) — начинать с самого короткого.
4. `record_idx` → запись в `Record Block` → координаты и поля.

Это соответствует FTS5-поведению `AND` + префикс, причём без ограничения
`prefix='2 3 4'` (поддерживаются произвольные длины префикса).

## 6. Этапы реализации

### Этап 1. Общий стемминг/токенизация

- Вынести `Indexer::stem_text` в `src/stem.rs` (`stem_text`, `tokenize`,
  `stem_tokens`).
- Использовать в `src/indexer.rs` и `src/compact.rs`.
- Тесты на паритет: `stem_text("Тверская улица")` одинаково для обоих путей.

### Этап 2. Структуры и writer

- В `src/compact.rs` добавить `FtsIndex` (словарь + постинги).
- В `CompactWriter::build`:
  1. пройти по объектам, собрать `(token, record_idx)` в два `HashMap`
     (address / named);
  2. отсортировать токены и постинг-листы, закодировать дельты varint;
  3. вычислить смещения секций;
  4. записать `Section Directory` и новые секции.
- Прогресс-бары для «Сборка FTS-индекса» (адреса и POI отдельно или вместе).

### Этап 3. Заголовок и section directory

- Поднять `version` до 2.
- Записать `Section Directory` после заголовка.
- Обновить `Header`/смещения так, чтобы старые 4 секции читались по-прежнему.

### Этап 4. Чтение/тесты паритета

- Unit-тесты на токенизацию, дельта-кодирование, сортировку, roundtrip
  build→query на маленьком наборе.
- Тест паритета: одинаковые запросы к SQLite FTS5 и к компактному FTS дают
  одинаковый набор `record_idx` (по фикстуре).
- Обновить `inspect_bin.py` (печать новых секций) и, при необходимости,
  `search_pool.py`.

### Этап 5. Бенчмарк и размеры

- Собрать ЦФО (`central-fed-district`) в `.bin` до/после, измерить размер и
  время сборки.
- Измерить: количество уникальных токенов, размер словаря и постингов,
  сжатие zstd.
- При необходимости — сжатие постингов (фаза 2).

### Этап 6. Документация и примеры чтения

- `DATABASE.md`: добавить раздел формата v2, layout FTS, C-структуры и
  псевдокод поиска.
- `README.md`: обновить описание компактного формата и «больше не строим индекс
  на устройстве».

## 7. Сопутствующие ограничения (важно для «Россия»)

Текущий `String Pool` использует индексы `u16` (максимум 65535 уникальных
строк). Для всей России уникальных строк (улицы + названия + города) почти
наверняка больше 65535 — это уже существующий риск переполнения, не связанный
напрямую с FTS, но критичный для целевого региона.

Рекомендация: в рамках v2 перевести индексы строк (`city_idx`, `street_idx`,
`name_idx`, `housenumber_idx`, `postcode_idx`, `country_idx`) с `u16` на `u32`
(или `u24` как компромисс), а `String Pool` — на `u32`-счётчик. Это меняет
размеры записей и все C/Python-структуры, поэтому делать сразу вместе с
version bump.

FTS-словарь токенов от этого не зависит (там сразу `u32`-смещения и inline
строки), но строить его поверх переполненного `String Pool` бессмысленно.

## 8. Оценка размера (ориентировочно)

Для ЦФО (~1.92M объектов после дедупликации):

- словарь токенов: порядка 100–300k уникальных токенов × ~20–40 Б ≈ 4–12 МБ;
- постинги: ~1.9M адресов × ~3 токена ≈ 5–6M постингов, delta+varint ≈ 1–2 Б
  в среднем ≈ 6–12 МБ;
- итого FTS: ~10–25 МБ без zstd, заметно меньше после zstd.

Для всей России — примерно на порядок больше, но zstd и дельта-сжатие должны
удержать рост в приемлемых пределах. Точные цифры — замером на этапе 5.

## 9. Совместимость и откат

- `version=2` — новый формат; старые читатели должны проверять `version` и
  явно отказываться, а не читать «как v1».
- По умолчанию `--format compact` пишет v2 **с** FTS-индексом.
- Опционально флаг `--compact-no-fts` для случаев, когда нужен минимальный
  размер и индекс на устройстве всё же строится (обратная совместимость с
  поведением v1).

## 10. Открытые вопросы

1. Нужен ли field-scoped поиск (искать токен только в `street`, только в
   `name`), или достаточно единого потока токенов на сущность?
2. Нужно ли ранжирование (tf / категория) в v1, или достаточно булева AND и
   стабильного порядка?
3. Минимальная длина префикса для поиска (производительность при 1-символьных
   префиксах)?
4. Целевой лимит памяти сборщика для всей России (нужен ли external sort
   постингов вместо `HashMap`)?
