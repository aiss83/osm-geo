# План: FTS-индекс при ограниченном объёме ОЗУ

## 1. Проблема

Сейчас `src/fts.rs` строит индекс как `HashMap<String, Vec<u32>>`, то есть
держит в памяти **все постинги** и по одному `Vec<u32>` на токен.

Оценка по ЦФО (1,92 млн объектов после дедупликации):

- адресных постингов: ~8,5 млн;
- постингов POI: ~0,1 млн;
- уникальных токенов: адреса ~37 тыс., POI ~17 тыс.

Для всей России (примерно ×10 от ЦФО) постингов станет порядка 80–100 млн.
Только данные `u32` (~4 байта × 90 млн ≈ 360 МБ) плюс накладные расходы
`HashMap`/`Vec` легко выходят за комфортные пределы ОЗУ сборщика.

## 2. Ключевое наблюдение

Число **уникальных токенов** невелико (сотни тысяч, а не десятки миллионов),
поэтому словарь `токен → u32 id` можно спокойно держать в ОЗУ. Проблема —
именно объём **постингов** (списки `record_idx`).

Значит, достаточно убрать из ОЗУ постинги, а не сам словарь.

## 3. Целевая структура

Вместо `HashMap<String, Vec<u32>>` используем два этапа:

1. **Словарь токенов** `HashMap<String, u32>` — остаётся в ОЗУ.
2. **Постинги** — пишутся в виде пар `(token_id: u32, record_idx: u32)` во
   временный файл, затем сортируются внешней сортировкой и группируются в
   потоке.

## 4. Алгоритм (external sort)

### Этап A. Назначить id токенам

Один проход по `records`:

- для каждого токена получить/создать `token_id` из `HashMap<String, u32>`;
- параллельно писать пару `(token_id, record_idx)` в буфер/файл.

### Этап B. Сортировка пар

- Накопить пары чанками фиксированного размера (например, 16–64 МБ);
- каждый чанк отсортировать в памяти по `(token_id, record_idx)` и записать
  как отдельный run во временный файл;
- выполнить k-way merge run'ов в итоговый отсортированный файл.

### Этап C. Группировка и запись постингов

Один проход по отсортированным парам:

- для каждого `token_id` собрать подряд идущие `record_idx`;
- закодировать их дельтами через varint и дописать в секцию postings;
- зафиксировать в словаре `(token, postings_offset, postings_count)`.

Пиковая память на этапе C — только размер одного run + словарь токенов.

## 5. Упрощённый путь для малых регионов

Если суммарный объём пар помещается в ОЗУ, можно не ходить в диск:

- писать пары в плоский `Vec<(u32, u32)>` (8 байт/пара);
- отсортировать в памяти;
- сгруппировать и закодировать.

Для ЦФО это ~8,5 млн пар × 8 байт ≈ 68 МБ — приемлемо. Для России уже ~700 МБ,
поэтому нужен порог переключения:

- при `pairs * 8 < порог` → in-memory flat sort;
- иначе → external sort.

## 6. Формат временных файлов

- Пары little-endian: `token_id: u32`, `record_idx: u32`.
- Run-файлы и итоговый отсортированный файл хранят те же 8-байтные записи.
- Файлы класть в `std::env::temp_dir()` или рядом с выходным `.osmg`, удалять
  после сборки.

## 7. Этапы реализации

1. Рефакторинг `FtsIndex` на интерфейс «словарь + поток постингов».
2. In-memory flat sort (`Vec<(u32,u32)>`) как первый вариант, покрыть тестами.
3. Чанкированный external sort + k-way merge.
4. Автовыбор стратегии по оценке объёма.
5. Бенчмарк на ЦФО и (по возможности) на РФ: время сборки, пиковое ОЗУ.

## 8. Критерии приёмки

- Пиковое ОЗУ сборки для РФ ≤ целевого лимита (например, 1–2 ГБ).
- Результат `.osmg` идентичен текущему по токенам и постингам (byte-compatible).
- Юнит-тесты на группировку, delta-кодирование и внешнюю сортировку.
