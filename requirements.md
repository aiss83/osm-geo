0. Область применения

Программа является ETL-пайплайном (Extract–Transform–Load): она загружает геопространственные данные из OpenStreetMap, обрабатывает их и формирует готовую базу данных для последующего применения на мобильных устройствах. Программа НЕ включает встроенный поисковый движок (Query Engine) — её задача исключительно подготовка данных. Потребителем выходной базы является сторонняя библиотека парсера и поиска, работающая на Android/iOS.

Программа выполняется на серверных/desktop-платформах (Linux, macOS, Windows) в ходе CI/CD-пайплайна. Готовый файл базы данных копируется на мобильное устройство как статический ресурс — через assets, загрузку на устройство, или A/B-обновление.

Основной язык поиска — русский. Английский язык допустим только в названиях объектов (поле name:en и другие языковые варианты тега name:*).

1. Цели и назначение

Разработать программу на языке Rust для подготовки компактной офлайн-базы данных геокодирования на основе открытых геопространственных данных (OpenStreetMap). База данных должна обеспечивать быстрый поиск географических координат по текстовому адресу или названию места и быть достаточно компактной для использования на мобильных устройствах (Android/iOS).

Ключевые требования:

Компактный размер базы данных (целевой ориентир — не более 100–200 МБ для данных по всей стране, 1–2 ГБ для планеты)
Быстрый поиск (миллисекундные задержки на мобильном устройстве)
Полная офлайн-работа без необходимости подключения к интернету
Поддержка международных адресов (многоязычность, различные форматы адресов)
2. Функциональные требования

2.1. Загрузка исходных данных

Поддержка загрузки данных OpenStreetMap в формате PBF (Protocol Buffer Binary) из общедоступных источников:

Geofabrik (https://download.geofabrik.de)
BBBike (https://download.bbbike.org/osm/planet/)
Возможность указания региона (страна, область, город) для загрузки
Поддержка инкрементальных обновлений (загрузка только изменений с определённой даты) — факультативно, в post-MVP
2.2. Обработка и парсинг данных

Парсинг PBF-файлов с использованием Rust-библиотек (например, osmpbf-rs или osmic)
Извлечение адресной информации из тегов OSM:

addr:housenumber, addr:street, addr:city, addr:postcode, addr:country
name, name:en, name:ru и другие языковые варианты
Альтернативные названия (alt_name, old_name, loc_name)
Обработка точек (nodes), линий (ways) и отношений (relations)
Нормализация адресов (приведение к единому формату, удаление дубликатов)
2.2.1. Языковая модель

Основной язык поиска — русский. Английский язык используется исключительно в названиях объектов (поле name:en и другие языковые варианты тега name:*).

Требования к обработке русского языка:

Токенизация с учётом кириллицы — корректное разбиение текста на токены, включая символы кириллицы, цифры и смешанные строки
Стемминг / лемматизация — учёт русской морфологии (падежи, склонения, словоформы). Минимально приемлемое решение — snowball-стеммер для русского языка. Оптимальное решение — полноценная лемматизация (например, через pymorphy3-словари, адаптированные для Rust)
2.2.2. Модель данных

Данные делятся на два типа сущностей:

Address — иерархический адрес, привязанный к дому/зданию/участку:

country:      Option<String>   — страна (addr:country, нормализованный)
city:         Option<String>   — город (addr:city либо admin_centre отношения)
street:       Option<String>   — улица (addr:street)
housenumber:  Option<String>   — номер дома (addr:housenumber)
postcode:     Option<String>   — почтовый индекс (addr:postcode)
point:        (f64, f64)       — координаты (широта, долгота)

NamedObject — именованный объект без жёсткой адресной привязки (POI, коммерческие и культурные объекты, памятники):

name:         String           — основное название (name / name:ru — обязательно)
name_alt:     Vec<String>      — альтернативные названия (alt_name, old_name, name:en, loc_name, …)
category:     Option<String>   — категория (amenity, tourism, shop, historic, leisure, …)
address_hint: Option<Address>  — неполная адресная привязка (addr:* теги объекта)
point:        (f64, f64)       — координаты (широта, долгота)

Памятники, кафе, музеи и другие POI, как правило, не имеют прямой привязки к адресу дома/улицы (addr:street, addr:housenumber). Они попадают в категорию NamedObject. Поиск по ним идёт по name / name_alt, с опциональной фильтрацией по category и address_hint.

2.3. Построение индекса для поиска

Индексы строятся на этапе сборки базы данных и сохраняются в выходной файл. Потребительская библиотека использует готовые индексы.

Полнотекстовый индекс (SQLite FTS5):

Конфигурация токенизатора unicode61 с поддержкой кириллицы
Кастомный стеммер для русского языка (словарь лемм или snowball-стеммер)
Индексация поля name + name_alt для NamedObject (единое полнотекстовое поле)
Индексация полей country, city, street, housenumber для Address (раздельные поля для префиксного/иерархического поиска)
Поиск по частичным совпадениям (префиксный поиск средствами FTS5 prefix queries)
Поддержка нечёткого поиска (typo tolerance) — через FTS5 с триграммами или отдельный индекс

Пространственный индекс (SQLite R*Tree):

Индексация координат (широта, долгота) всех объектов
Поддержка запросов по bounding box
Поддержка поиска по фокусной точке (сортировка результатов по расстоянию)

Категориальный индекс:

Отдельная таблица или колонка для фильтрации по категориям (amenity, tourism, shop, …)

2.4. Формат выходной базы данных

Основной формат: SQLite (.db, единый файл). Обоснование выбора:

Нативная поддержка на Android и iOS (встроена в ОС)
FTS5 — зрелый полнотекстовый движок с поддержкой кастомных токенизаторов
R*Tree — встроенное расширение для пространственных индексов
Memory-mapped I/O (PRAGMA mmap_size)
Транзакционность и WAL-режим
Проверенная работа с файлами до 2 ГБ

Резервный формат для планетарной базы: собственный бинарный формат. Применяется, если SQLite-база для всей планеты превышает целевой размер в 2 ГБ и не поддаётся оптимизации сжатием.

Схема SQLite (целевая):

-- Основная таблица объектов
CREATE TABLE objects (
    id         INTEGER PRIMARY KEY,
    type       INTEGER NOT NULL,   -- 0 = Address, 1 = NamedObject
    lat        REAL    NOT NULL,   -- широта
    lon        REAL    NOT NULL,   -- долгота
    data       BLOB    NOT NULL    -- сериализованные поля (JSON/protobuf/msgpack)
);

-- Пространственный индекс
CREATE VIRTUAL TABLE objects_rtree USING rtree(
    id, min_lat, max_lat, min_lon, max_lon
);

-- Полнотекстовый индекс для NamedObject
CREATE VIRTUAL TABLE fts_named USING fts5(
    name, name_alt, category,
    tokenize = '...',   -- кастомный токенизатор с русским стеммером
    content  = ''
);

-- Полнотекстовый индекс для Address
CREATE VIRTUAL TABLE fts_address USING fts5(
    country, city, street, housenumber, postcode,
    tokenize = 'unicode61',
    content  = ''
);

-- Индекс по категориям
CREATE INDEX idx_objects_category ON objects(category) WHERE type = 1;

Требования к выходному файлу:

Единый SQLite-файл (.db), содержащий все таблицы и индексы
Поддержка сжатия на уровне файла (Zstandard) для транспортировки на устройство
Метаданные в таблице meta: версия схемы, регион, дата сборки, хеш (SHA-256) исходного PBF, статистика (кол-во объектов)
Возможность A/B-обновления: замена файла базы без потери данных на стороне потребителя

2.5. Экспорт и интеграция

Экспорт подготовленной базы в единый SQLite-файл (.db), готовый к копированию на мобильное устройство
Генерация сопроводительного файла метаданных (JSON): версия программы, регион, дата сборки, SHA-256 хеш файла БД, количество объектов, размер файла
Контракт для мобильной библиотеки-потребителя:
Ожидается, что библиотека открывает файл через стандартное SQLite API (android.database.sqlite / iOS SQLite)
Библиотека выполняет запросы через FTS5 (MATCH) и R*Tree (WHERE min_lat/max_lat/…)
Библиотека отвечает за: нормализацию пользовательского запроса и ранжирование результатов
CLI-интерфейс с поддержкой:

build --region <REGION> --output <PATH> — сборка базы для региона
query --db <PATH> "запрос" — тестовый поиск (для валидации собранной базы)
info --db <PATH> — вывод метаданных о собранной базе

2.6. CI/CD и автоматизация сборки

Пайплайн автоматической сборки баз данных для целевых регионов:

Docker-образ с программой-сборщиком и всеми зависимостями
Запуск сборки по расписанию (еженедельно, синхронизированно с обновлениями Geofabrik)
Параллельная сборка для разных регионов (матрица в CI)
Готовые .db-файлы — артефакты CI, выгружаются в GitHub Releases или внутреннее хранилище
Проверка целостности артефактов: сверка SHA-256, тестовый query-запрос по эталонным адресам

3. Требования к производительности и размеру

Параметр	Целевое значение
Размер базы для региона (Россия)	≤ 200 МБ
Разбор PBF-файла	≤ 10–20 минут для региона
Время поиска (на мобильном устройстве)	≤ 50 мс (в среднем, P50)
Потребление ОЗУ при построении индекса	≤ 2 ГБ
Потребление ОЗУ при поиске (на мобильном)	≤ 50–100 МБ
Поддерживаемые регионы	Весь мир (планетарная база — ≤ 2 ГБ)
Качество поиска (precision@1)	≥ 80% на эталонном наборе из ≥200 запросов

Ориентиры: GeoDesk показывает, что база данных может занимать лишь на 20–50% больше, чем исходный PBF-файл. butterfly-osm демонстрирует возможность обработки планеты с использованием < 1 ГБ ОЗУ.

SQLite должен быть скомпилирован с флагами:

SQLITE_ENABLE_FTS5
SQLITE_ENABLE_RTREE
SQLITE_ENABLE_LOAD_EXTENSION (для кастомного токенизатора, если потребуется)
SQLITE_DEFAULT_MMAP_SIZE=268435456 (256 МБ)

Эталонный формат для хранения данных внутри SQLite (поле data BLOB) — MessagePack (rmp-serde). Компактнее JSON, быстрее парсится на стороне потребителя.

6. Этапы разработки

Этап 1: Исследование и прототипирование (3–4 недели)

Анализ формата PBF и структур OSM
Изучение существующих решений (Airmail, GeoDesk, Nominatim, osmic)
Оценка SQLite FTS5 для русского языка: тестирование стеммеров, токенизаторов, качества поиска
Прототип схемы SQLite и бенчмарк размера/скорости на одном регионе
Выбор стратегии лемматизации (snowball vs pymorphy3-словари)
Разработка MVP для небольшого региона (область РФ)

Этап 2: Основная разработка (4–6 недель)

Реализация загрузчика и парсера PBF
Реализация двухтиповой модели данных (Address + NamedObject)
Реализация модуля записи в SQLite: FTS5-индексы, R*Tree, таблицы объектов
Реализация кастомного токенизатора FTS5 с русским стеммером
Модуль финализации: проверка целостности, сжатие, метаданные
Сборка базы для РФ и проверка размера / качества поиска

Этап 3: Оптимизация и тестирование (3–4 недели)

Оптимизация размера базы данных (VACUUM, сжатие, дедупликация)
Тестирование производительности на различных регионах (РФ, Европа, СНГ)
Тестирование качества поиска (precision@1, recall) на эталонном наборе запросов
Тестирование на мобильных устройствах (эмуляторы / реальные устройства)
Исправление ошибок и доработки
Если SQLite для планеты выходит за 2 ГБ — прототипирование собственного бинарного формата

Этап 4: Финальная сборка, CI/CD и документация (1–2 недели)

Сборка бинарных файлов для целевых платформ (Linux, macOS, Windows)
Написание документации и инструкций
Создание CI/CD пайплайна (Docker + GitHub Actions / GitLab CI)
Настройка еженедельной автоматической сборки для регионов
Публикация артефактов (GitHub Releases / внутреннее хранилище)
Создание эталонного набора запросов (≥ 200) для проверки качества

Post-MVP (за горизонтом Этапа 4):

Инкрементальные обновления базы данных
Собственный бинарный формат для планетарной базы (если потребуется)
Поддержка дополнительных источников данных (ФИАС, ГАР, OpenAddresses)

7. Критерии приёмки

Функциональность:

Программа успешно собирает SQLite-базу данных для выбранного региона из PBF-файла

8. Возможные риски и способы их mitigation

Риск	Способ mitigation
Русская морфология ухудшает качество поиска	Прототипирование нескольких стеммеров/лемматизаторов в Этапе 1; выбор лучшего по precision на тестовом наборе
Большой размер базы данных	Использовать сжатие (Zstd), фильтрацию не-адресных объектов, агрегацию; SQLite VACUUM; запасной план — собственный бинарный формат
Низкая производительность поиска	SQLite FTS5 оптимизирован для миллисекундного поиска; memory-mapped I/O; индексы строятся на этапе сборки
Сложность обработки OSM-отношений	Использовать проверенные библиотеки (osmic, par-osm-rust)
Неполнота адресных данных в OSM (особенно в РФ)	Post-MVP: поддержка дополнительных источников (ФИАС, ГАР, Who's On First, OpenAddresses); на начальном этапе — документирование ограничений
Большое потребление памяти при индексации	Потоковая обработка PBF без загрузки всего набора в память; FTS5 и R*Tree строятся инкрементально в SQLite
SQLite не влезает в 2 ГБ для планеты	Запасной план: собственный бинарный формат с компактной структурой; решение принимается по результатам бенчмарка в Этапе 3
